# MVP 결정 문서 (swallow)

이 문서는 컨시어지 기반 안경 예약 MVP를 어디까지 만들고, 무엇을 나중에 미룰지 합의한 내용을 기록한다.
작업 중 범위가 흔들릴 때 이 문서를 기준으로 자른다.

---

## 1. 프로젝트 목표 및 검증 가설

- **목표:** 한국에 온 외국인이 언어·예약·가격 범위·면세·매장 찾기 부담 없이 안경을 예약할 수 있게 돕는 서비스
- **시작 형태:** 서울 1개 권역의 다국어 예약 컨시어지 (플랫폼이 아니라 사람 개입이 포함된 예약 보조 서비스)
- **핵심 가설:** 외국인이 언어 장벽 없이 예약 흐름을 경험하면 실제 문의·예약·방문으로 이어진다
- **초기 검증 질문:**
  - 문의 → 접수 → 예약 확정 → 방문 완료 흐름이 사람 손으로도 돌아가는가
  - 어떤 언어/채널에서 문의가 들어오고, 어떤 지점에서 막히는가
  - 매장 정보가 “참고용”이어도 고객 신뢰와 전환이 생기는가

---

## 2. MVP 범위

### 포함

- 고객용 로그인 (Google 소셜 로그인 + 이메일 식별)
- 다국어 랜딩 페이지 (서비스 소개, 왜 한국에서 안경이 편한지, 절차, 신뢰 요소)
- 매장 정보/위치 확인 (초기에는 운영자가 직접 고른 3~5개 매장을 수동 등록, 지도+리스트)
- 예약 접수 폼 (희망 날짜/시간대, 시력검사 포함 여부, 예산 범위, 지역/매장 선호, 사용 언어, 메모)
- AI 기반 접수 정리 및 보완 제안 (요약, 누락 정보 질문 제안, 운영자용 티켓 생성)
- 운영자 뷰 (접수 목록, 매장 후보, 상태 변경, 매장 확인 메모, 고객 안내 초안)
- 고객 상태 조회/안내 (신청 링크/코드 또는 세션 기반, 확정·변경·취소·방문 안내)
- 확정·유의·면세·길찾기 안내 템플릿 발송 (이메일/메신저/문자 등 사람이 쓰던 채널 우선)

### 제외 (검증 이후로 미룸)

- 프로필/고객 계정 기능 고도화
- 결제·정산 연동
- 인앱 실시간 채팅/콜센터
- 매장 파트너용 포털 (입점, 슬롯 관리, 정산 등)
- 리뷰·평점·신뢰 시스템
- 다중 권역 확장
- 네이티브 앱

---

## 3. 핵심 사용자 흐름

1. 고객이 영어/한국어로 “내일 오후, 시력검사 포함, 예산 20만 원”처럼 짧게 입력
2. 서비스가 조건에 맞는 매장 후보를 요약/추천하고, 부족한 정보는 1~2회 보완 질문으로 제안
3. 고객이 입력 확정 → 접수 저장
4. 운영자가 접수 내역을 보고 매장에 가능 여부/가격 범위/소요 시간/시력검사 필요 여부를 확인·조정
5. 운영자가 예약 확정/조정/반려 처리 후 고객에게 다국어 확정 안내 발송
6. 방문 전/당일 문제 발생 시 채팅 또는 메신저로 재조율 (사람 대응)
7. 고객은 자신의 신청 건 상태를 조회·수정·취소 가능

---

## 4. 기술 스택 및 아키텍처 방향

- **프레임워크:** Next.js App Router
- **워크스페이스:** pnpm + Turborepo 모노레포 (이미 `swallow/`에 골격 존재)
- **데이터베이스/인증:** Supabase (Postgres + Auth + 향후 어드민/파트너 확장용)
- **다국어:** `next-intl` 또는 JSON 기반 메시지 키 관리 (KR/EN 우선, JP는 조기 추가 옵션으로 확장 가능하게)
- **렌더링:** 랜딩/매장 정보 등은 정적/ISR 위주로 빠르게, 예약 폼/운영자 뷰는 서버 액션/서버 컴포넌트 중심으로 처리
- **운영 도구:** 초기에는 스프레드시트/메신저 병행도 허용, Supabase 대시보드 또는 작은 어드민 페이지를 최소 운영 뷰로 사용

---

## 5. 인증/식별 전략

- **고객 진입은 낮게:**
  - Google 소셜 로그인 + 가벼운 이메일 식별(마법 링크/이메일 OTP 등)을 병행
  - 목표는 “계정 생성 부담”이 아니라 “접수 식별 + 상태 조회/수정 가능 + 연락처 확보”
  - 로그인하지 않은 고객도 신청 링크/코드로 자신의 건을 조회·수정·취소할 수 있게 설계
- **운영자/내부 스태프는 제대로 보호:**
  - Supabase Auth 기반 로그인, 보호 라우트/대시보드
  - 접수·확정·조정·고객 응대·상태 변경 등 운영 기능은 인증 이후에만 접근
- **데이터 분리:**
  - 예약/신청 데이터는 소유자/역할/접근 범위를 분리 가능하게 설계
  - 고객-facing 식별과 내부 운영 식별을 같은 예약 모델 위에서 다루되, 접근 범위를 분리
- **언어/문구 분리:**
  - 로그인 버튼, 실패/재시도 메시지, 인증 이메일 본문, 링크 만료 문구 등은 언어별 문구로 분리
  - 나중에 JP를 붙여도 문구/프롬프트/템플릿 세트 추가로 끝나도록 구조 개방

---

## 6. 다국어 전략

- **시작:** 한국어 + 영어
  - 대상/범용성/안정성 우선
  - 랜딩, 매장 정보, 예약 폼, 확정 안내 템플릿을 KR/EN 두 언어로 동일한 정보 구조로 제공
- **확장 옵션:** 고객 반응 신호(일본어 문의/선호, 언어별 전환 차이, 운영자 체감 등)에 따라 일본어를 이른 시일에 추가
- **원칙:**
  - 언어별 문구/템플릿/AI 프롬프트 변형은 분리 가능하게
  - 레이아웃은 영문 길어지는 경우, 일본어 짧아지는 경우에 버티도록 유연하게
  - 확정성 정보(가격 범위, 제작 소요, 가능 여부, 시력검사 필요 여부, 면세 가능 범위)는 “참고용”임을 명시하고, 최종 확정은 운영자·매장 확인 영역

---

## 7. AI 역할 경계

- **AI가 하는 일:**
  - 고객이 입력한 자유 텍스트 + 핵심 선택지를 정리
  - 요약문 생성, 누락/모호 정보에 대한 보완 질문 제안
  - 운영자용 신청 티켓 정리, 고객용 요약/안내 문구 번역/정리 보조
- **AI가 하지 않는 일:**
  - 매장 실제 가능 여부, 정확한 가격 범위, 시력검사 필요 여부, 제작 소요 시간, 면세 가능 여부를 단정하지 않음
  - 예약 확정/반려/조정을 대신 결정하지 않음
- **운영 원칙:**
  - AI는 접수·정리·보조까지만 담당
  - 확정성 정보는 운영자 + 매장 확인 영역으로 분명히 분리
  - AI는 틀릴 수 있으므로 운영자용 초안은 수정 가능하게 남기고, 고객에게 단정 발송하지 않음

---

## 8. 상태 관리 및 알림

- **상태 흐름 예시:**
  - 접수 → 확인 중(매장 연락/가능 여부 확인) → 확정/조정 → 안내/방문 → 완료/취소
- **식별/조회:**
  - 로그인 세션 또는 신청 링크/코드로 자신의 건 조회
  - 언어와 무관하게 상태 전환/식별/알림이 작동하도록 설계
- **알림:**
  - 초기에는 이메일/메신저/문자 등 운영자가 이미 쓰는 채널로 사람 대응 우선
  - 확정 시 다국어 안내 템플릿 발송, 변경/취소/재조율 알림도 같은 방식으로 처리
  - 인앱 채팅/자동 콜센터류는 제외

---

## 9. 검증 지표 및 다음 단계

### MVP에서 볼 지표

- 언어별/채널별 문의 건수
- 접수 전환율 (문의 → 실제 접수)
- 예약 확정률, 방문 완료률
- 언어권별 재방문/추천 의사 또는 긍정 반응 여부
- 운영자 처리 시간/병목 지점 (어디서 가장 시간이 드는가)
- AI 정리/보완이 실제로 운영에 도움이 되는지, 수기 정리 대비 효율

### 다음 단계 판단 기준

- 실제 문의가 들어오고, 예약·방문 흐름을 몇 번 돌려 본 뒤
- 매장 연결이 매끄러운지, 고객이 상태 가시성/다국어 안내를 얼마나 중요하게 느끼는지 확인
- 운영 부담이 사람 1명 수준을 넘는지, 자동화/플랫폼화가 필요한 지점이 보이는지 확인
- 플랫폼이 필요하면 그때 백오피스/파트너 포털/결제/정산/다중 권역 등 구조를 다시 판단

---

## 10. 의사 결정 원칙

- **MVP는 기능 완결성보다 흐름 존재 증명이 우선**
- **범위 확장보다 흐름 안정화/전환 확인 먼저**
- **확정성 정보와 참고용 정보를 UI에서 분명히 분리**
- **AI는 보조, 사람과 매장 확인이 핵심**
- **언어/인증/데이터/템플릿은 나중에 JP·계정·플랫폼 확장이 들어와도 다시 짜지 않게 분리해 둠**
- **MVP 단계에서 “아직 정해지지 않은 것”은 추측으로 덮지 말고, 실제 운영으로 확인한 뒤 판단**
